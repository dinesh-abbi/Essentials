# Project Orientation (for Claude / any agent working in this repo)

This section exists so a fresh session can get productive in one read instead of
re-discovering the same traps. It's operational knowledge, not a feature list —
see `README.md` for the user-facing feature rundown and `BARCODE_ALARM.md` for the
alarm subsystem's design doc.

## What this is

**Essentials** (package `com.catalyst.essentials`) is a personal Android utility
app: hydration tracking, expense tracking, camera check-in/attendance, a
barcode-dismiss alarm, a home-screen hydration widget — and, since v1.2.0,
the former **Catalyst** fitness app: training (weekly split, session logging),
fuel (28-day meal plan, restock list). AI/chat features were removed in
v1.3.0. The
Catalyst repo is retired; `docs/CATALYST_MERGE.md` maps every old feature to
its new home. Single user-facing app, single developer, distributed by
sideloaded APK + self-hosted OTA updates via GitHub Releases (not the Play
Store, not EAS-hosted builds).

Read `RULES.md` too — it is the short list of things that must stay true.

Stack: Expo SDK 56, React Native 0.85.3, React 19.2, Expo Router v4
(file-based routing), New Architecture enabled (Fabric + TurboModules,
`ExpoReactHostFactory`/`ReactHost`, **not** the legacy bridge). Firebase
(Auth + Firestore) for the backend. Reanimated 4 for animation.

## The native Android side — read this before touching `android/` or widgets

This is the sharpest edge in the repo and has already caused a real shipped
crash once (duplicate `"WidgetStorage"` native module — fixed, see git log
around the widget-native rewrite). The setup:

- **Since v1.2.0 every native file is reproducible.** The alarm/QR code
  that used to live only in `android/` was decompiled out of the v1.1.2
  release APK (jadx), rewritten as Kotlin in `native-android/`, and is
  re-applied by `withEssentialsNative.js`. `expo prebuild --clean` is now
  safe. The old tracked `android/app/build.gradle` + `gradle.properties`
  were untracked — the prebuild template + plugins generate equivalents
  (ML Kit dependency included).

- **`android/` is gitignored and NOT regenerated on a normal build.**
  `build.sh` explicitly skips `expo prebuild` whenever `android/` already
  exists ("Skipping native project regeneration to leverage Gradle caching").
  That means changes to `app.json`'s `plugins`, or to any config plugin's
  `.js`, **do not take effect** until you either delete `android/` and let it
  regenerate, or manually replicate what the plugin would have done. Editing
  `widget-native/*.kt` alone and rebuilding does *nothing* — see next point.

- **`widget-native/` is the only tracked source for the widget's native code.**
  `withWaterWidget.js` copies `widget-native/*.kt` and `widget-native/res/**`
  into `android/app/src/main/java/com/catalyst/essentials/` and
  `android/app/src/main/res/`, and patches the manifest + `MainApplication.kt`
  — but **only when it actually runs**, which per the point above it usually
  doesn't. Whenever you change anything under `widget-native/`, manually sync
  it into `android/` too:
  ```bash
  cp widget-native/*.kt android/app/src/main/java/com/catalyst/essentials/
  cp -r widget-native/res/* android/app/src/main/res/
  ```
  Then rebuild. Forgetting this step is the single most likely way to ship a
  build where your widget edits silently don't exist.

- **Alarm + QR native code lives in `native-android/`.** Same rule as the
  widget: edit the tracked `.kt`, then either re-run prebuild or copy the
  file into `android/app/src/main/java/com/catalyst/essentials/` before a
  fast `gradlew` build. Both modules are registered by
  `EssentialsNativePackage` (`"AlarmScheduler"`, `"QrCodeScanner"`); the
  widget keeps `WidgetPackage` (`"WidgetStorage"`).

- **Watch for duplicate `getName()` native module strings.** Two different
  `ReactPackage`s registering a module under the same name is a fatal crash at
  app startup (native module registry collision), not a build error — it
  compiles fine and dies on first launch. This exact bug shipped once (an old
  `WidgetStorageModule` and the new `WidgetDataStore` both claimed
  `"WidgetStorage"`). Before adding a new native module, grep for its intended
  name across `android/app/src/main/java/com/catalyst/essentials/*.kt`.

- **RemoteViews (the widget) is a much smaller sandbox than a normal Activity.**
  No arbitrary custom views, no live/looping animation without a battery-costly
  polling service, no direct filesystem/AsyncStorage access from Kotlin. The
  patterns already in use and safe to extend:
  - Data in/out: `WidgetDataStore` (native module `"WidgetStorage"`) written to
    from `src/utils/WidgetSync.ts`, backed by `SharedPreferences`
    (`essentials_widget_prefs`), read by `WaterWidgetProvider` on every
    `AppWidgetManager` update.
  - Instant on-widget actions without opening the app: `WidgetQuickLogReceiver`
    (a `BroadcastReceiver`, triggered via `PendingIntent.getBroadcast`, exported
    because the launcher process is what actually fires it) does an optimistic
    `SharedPreferences` bump + repaint, then starts `WidgetQuickLogTaskService`
    (a `HeadlessJsTaskService`) to run the `WidgetQuickLog` headless JS task
    registered in `WidgetSync.ts` — this persists the log for real through the
    normal `WaterStorage`/Firestore path with zero UI. `HeadlessJsTaskService`
    is confirmed New-Architecture-compatible in this RN version (checks
    `ReactNativeNewArchitectureFeatureFlags.enableBridgelessArchitecture()` and
    uses `MainApplication.reactHost`), so this pattern is safe to reuse for
    other native modules.
  - Size-adaptive layout: `WaterWidgetProvider.updateWidget()` reads
    `OPTION_APPWIDGET_MIN_WIDTH`/`MIN_HEIGHT` from `AppWidgetManager` and picks
    one of five layout tiers (tiny/compact/tall/wide/large). If you add a
    tier or change a threshold, remember a "tiny" check needs **both**
    dimensions small (`&&`, not `||`) — a wide-but-single-row widget has the
    same height as a true 1x1 cell on most launchers, so an OR there
    misclassifies every wide/large placement as tiny (this shipped once too).
  - Tap feedback: a `<ripple>` drawable (`widget_ripple_root.xml`,
    `widget_quicklog_*_bg.xml`) is the only reliable "animation" a widget gets
    for free — transparent at rest, paints only while pressed. Don't reach for
    anything fancier than this without confirming it actually renders across
    launchers; there's no device in this dev environment to verify on (see
    below), so prefer well-documented, conservative RemoteViews features over
    anything exotic.

## App architecture conventions

- **Routing**: `expo-router`, file-based, under `src/app/`. `(tabs)/` is the
  bottom-tab group; everything else (`water/`, `purchases/`, `alarm/`, `upi/`,
  `attendance.tsx`) is registered as a flat `Stack.Screen` in the root
  `src/app/_layout.tsx` — there's no per-feature `_layout.tsx` nesting anymore
  (removed in the report-view consolidation, see `CHANGELOG.md`).
- **Auth guard**: `src/app/_layout.tsx`'s `AppStack` redirects based on
  `AuthContext` + current route segment. The `alarm` segment is explicitly
  exempted from the guard (`if (inAlarmGroup) return`) so the alarm screen can
  launch on top of a locked/logged-out session.
- **Storage is local-first** (`src/utils/*Storage.ts`). Writes update the
  AsyncStorage cache and `SyncManager.queueAction(...)`, then return — never
  `await` Firestore or a reachability probe on a user action. The flusher
  (`SyncManager.syncOfflineData`, started by the root layout via
  `startBackgroundSync()`) pushes the queue after a short debounce, on every
  return to foreground, and on a back-off timer while anything is pending.
  Reads are cache-first: list collections use `createCollectionCache`
  (`localFirst.ts`), single docs/maps use `cacheFirst` (`userDocs.ts`); both
  revalidate from Firestore in the background (throttled) and emit
  `SyncManager.notifyDataChanged(scope)` when something changed. Screens that
  should update live use `useDataRefresh([...scopes], reload)`. New
  persisted data under `users/{uid}` should use `writeUserDoc` /
  `deleteUserDoc` (generic `doc_set`/`doc_delete` queue actions) rather
  than adding a new action type. Queue invariants: one lock around every
  read-modify-write; same-path `doc_set`s collapse (merges combine fields);
  `water_clear` carries explicit ids and must never delete the collection.
- **Widget sync**: any code path that changes water/purchases totals should
  call `WidgetSync.sync()` afterwards (grep existing call sites before adding
  a new mutation path) so the home-screen widget doesn't go stale.
- **Theming**: `src/constants/theme.ts` exports `Colors.light`/`Colors.dark`
  plus spacing/radius tokens; screens derive a local `colors` object from
  `useColorScheme()` rather than a ThemeProvider context. The widget's own
  `widget_colors.xml` (light) / `values-night/widget_colors.xml` (dark) is a
  hand-kept mirror of the same palette — update both sides if the palette
  changes.
- **Design system ("Glance", v1.3.0)**: a true-dark base with one vivid hue
  per area (`Hue` in theme.ts — water cyan, train coral, fuel lime, spend
  sunshine, check-in lavender, alarm pink, profile blue), Nunito for words
  and Doto (dot-matrix, monospaced, no ₹ glyph) for numerals. Signature
  pieces: `LargeHeader` (One UI title area), `Tile`/`ChunkyButton`/
  `IconBlob`/`Chip` (chunky surfaces with a sinking lip), `ProgressRing`
  (Apple rings), `DotMeter`/`LiveDot` (Nothing), `SettingRow`, `Segmented`,
  `StatTile`, `BarChart`, `Donut`, `ScanFrame`, `BigMessage`, `DateTimeSheet`,
  `Confetti`, and the `Droplet` mascot (Home, Water, login). Spend categories
  (icon + colour) live in `components/spend/categories.ts`; add/edit an expense
  through `ExpenseSheet`. Every looping animation must be gated on
  `useReducedMotion()`. See RULES.md §Design.
- **Visual hierarchy**: do *not* give every card the same fixed height. The
  home screen deliberately runs one tall hero card (hydration) above a shorter
  secondary stat row — uniform card heights are what made it read as a
  generated dashboard, and that was a specific piece of user feedback.

## Feature subsystems

Where each feature actually lives, and the non-obvious wiring in each. Screens
follow the routing/storage conventions above unless noted.

- **Training** (from Catalyst) — `(tabs)/train.tsx`, `train/week.tsx`,
  `train/brief.tsx` (`?kind=wake|go|complete`, the notification targets),
  `utils/TrainingStorage.ts`, `components/training/*`. The split is 7
  "slots"; `splitSlotFor(date, offset)` maps a weekday to a slot. The
  schedule offset is per-week local state that expires on Monday. Today's
  checklist/weights are local-only scratch (reset at local midnight); only a
  finished session is written (`workoutLogs`). Last-used weights pre-fill the
  stepper. A custom split saved by an older build (`training/split`) is still
  honoured; the week plan can reset it to the default.
  **Forma merge (v1.4.0):** rep-based moves are logged set by set
  (`SetEntry` in `DayState.sets`, `LoggedSet[]` on the session; `isSetBased`
  decides which moves). New fields are all optional so old sessions and custom
  splits stay valid. `ExerciseCatalog.ts` serves the static library
  (`data/training/exercises.json`, `muscles.json`); `musclesFor()` resolves a
  split move's muscles (`muscles` → `catalogId` → default split by name).
  `BodyMap`/`ExerciseArt` are react-native-svg ports (art data in
  `data/training/poses.ts`). Records (`TrainingRecords.ts`), muscle load/recap
  (`TrainingVolume.ts`) are computed from sessions, never stored. Stored:
  `goals/{id}`, `reviews/{monday}`, `training/favourites`. Screens:
  `train/explore`, `train/exercise/[id]`, `train/edit-day`, `train/progress`.
  See `docs/FORMA_MERGE.md`.
- **Fuel** (from Catalyst) — `(tabs)/fuel.tsx`, `utils/FuelStorage.ts`,
  `components/fuel/*`. Cycle position derives from a stored start date
  (`fuel/cycle`), not a counter. Meal logs are keyed by calendar date. Grocery
  ticks call `PurchasesStorage.savePurchase(..., 'Groceries')` and store the
  purchase id per restock window so unticking deletes the same purchase.
- **Routine reminders** — `notifications.ts` `rescheduleRoutineReminders()`:
  training wake/go (WEEKLY, skip recovery slots), meals (DAILY), restock
  (WEEKLY on the cycle-start weekday) on channel `routine#001`. Every
  scheduled notification has a deterministic identifier (`water-08`,
  `train-go-3`, `meal-lunch`, `restock`) so groups reschedule independently;
  a signature of their inputs skips needless rebuilds. Call it after changing
  the split, the offset, the cycle or the switches.
- **App lock** — `components/AppLock.tsx`, rendered by `AppStack` above the
  navigator; opt-in (`Preferences.isAppLockEnabled`), 5-minute grace, never
  over the `alarm` segment.

- **Hydration** — `src/app/water/*` + `(tabs)/index.tsx` hero card,
  `utils/WaterStorage.ts`. Mirrored to the home-screen widget via
  `utils/WidgetSync.ts` → native `WidgetStorage` module. Hourly reminder
  notifications (8 AM–10 PM) live in `utils/notifications.ts` and carry a
  `YES_ACTION` that logs 250 ml straight from the notification shade.
- **Expenses** — `src/app/purchases/*`, `utils/PurchasesStorage.ts`. Biometric
  lock on entry (`expo-local-authentication`). UPI QR flow in `src/app/upi/*`
  uses the native `QrCodeScanner` module + `withAndroidQueries.js` (Android 11+
  package-visibility queries for the UPI apps).
- **Attendance / check-in** — `src/app/attendance.tsx`, camera capture posted
  to a *user-supplied* Discord webhook (stored per-user in Firestore at
  `users/{uid}.discordWebhookUrl`, never in the repo). Setup UI is the
  expandable Discord panel in Profile.
- **Barcode alarm** — see `BARCODE_ALARM.md` for the full design. Native-only
  (foreground service + lock-screen activity + sensor muting); JS side is
  `src/app/alarm/{setup,screen}.tsx` and `utils/BarcodeAlarmStorage.ts`.
  **Its native code has no config-plugin backing** — see the native section above.
- **Home-screen widget** — `widget-native/` (tracked) → `android/` (generated).
  Five size tiers, instant quick-log without opening the app via
  `WidgetQuickLogReceiver` → `HeadlessJsTaskService`, and a local-date stamp
  (`KEY_SYNC_DATE_KEY`) that resets the cached daily total at midnight even if
  the app is never reopened.
- **Floating tab bar** — `components/app-tabs.tsx`. Real Android backdrop blur
  via `expo-blur`, which on Android needs an explicit `blurTarget` ref rather
  than blurring "whatever is behind" like iOS. Each tab screen wraps its root
  in `<BlurTargetView>` and registers that ref on focus through
  `utils/blurTarget.ts`; the bar reads whichever registered last. A tint layer
  sits over the blur so the Android <12 / unwired fallback still looks
  intentional. Bar dimensions come from `TabBar` in `theme.ts` — the single
  source of truth `BottomTabInset` is derived from, so screen bottom-padding
  can't drift out of sync with the bar's real size.
  - **Always pass `tint` to `<BlurView>`.** It defaults to `'default'`, which
    resolves to a *white* overlay (`rgba(255,255,255,…)` in expo-blur's
    `getBackgroundColor.ts`) and washes a dark-mode surface out to light grey.
  - **Scroll-reveal**: `utils/tabBarVisibility.ts` holds a module-level
    Reanimated mutable (`tabBarHidden`, 0 = shown, 1 = tucked away) plus a
    `useTabBarScrollHandler()` the tab screens attach to their
    `Animated.ScrollView`. It's a mutable written from the scroll worklet
    rather than React state because it updates every frame — going through
    React would re-render per frame and visibly stutter. Tab screens must use
    `Animated.ScrollView` (not `ScrollView`) for the handler to be a worklet,
    and must call `showTabBar()` in their focus effect so a prior scroll can't
    leave the bar stranded off-screen.
- **OTA updates & release notes** — self-hosted via GitHub Releases:
  - `utils/updates.ts` owns everything network/install: fetching the latest
    release, semver comparison (numeric, so 1.0.10 > 1.0.9), APK download with
    progress, and the `content://` handoff to Android's package installer.
    It also records the last version already offered (`markUpdateSeen` /
    `hasSeenUpdate`) so an update is surfaced once per release instead of
    nagging on every launch.
  - **The release body *is* the changelog markdown.** `publish-github.js` passes
    `changelogs/vX.Y.Z.md` to `gh release create --notes-file`, so
    `release.body` from the API can be fed straight into the parser. If you
    change the changelog format, `utils/changelogParser.ts` is what reads it.
  - `utils/changelogParser.ts` parses that markdown into typed sections
    (features / fixes / ui / build / commits) plus an inline tokenizer for
    `**bold**` and `` `code` ``. Hand-rolled on purpose: the format is known
    and narrow, and structured sections are what let the UI group, colour-code,
    and count items. Heading classification is word-boundary matched — a naive
    `includes('ui')` also matches "b**ui**ld". Unrecognised bodies (e.g.
    GitHub's `--generate-notes`) degrade into an "other" section, and a body
    that parses to nothing renders raw rather than blank.
  - `components/ChangelogView.tsx` is the shared presentational reader
    (full-width, two-column above a 700 dp breakpoint). `src/app/update.tsx`
    (modal, owns install + progress) and `src/app/whats-new.tsx` (Profile →
    App Version row) both render it, so the two can't drift.
  - `components/OTAUpdateChecker.tsx` renders nothing — it's the launch-time
    check that routes to `/update`. It waits for auth to resolve and requires a
    signed-in user so it can't race the auth guard's `/login` redirect, and it
    skips the `login`/`alarm`/`update` groups (never navigate away from a
    ringing alarm).

## Build & release workflow

- **Fast local iteration** (no prebuild, no publish):
  ```bash
  export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64   # JDK 17 required; Java 25 breaks the build
  cd android && ./gradlew assembleRelease
  ```
  On the Windows office PC: JDK 17 is at
  `C:\Program Files\Microsoft\jdk-17.0.20.101-hotspot`, the SDK at
  `%LOCALAPPDATA%\Android\Sdk` (platform 36, build-tools 36.0.0, NDK
  27.1.12297006, CMake 3.22.1); use `gradlew.bat` and
  `-PreactNativeArchitectures=arm64-v8a,armeabi-v7a` (no x86 — halves APK
  size and build time). `build.sh`/`publish-github.js` assume a POSIX shell.
  Output: `android/app/build/outputs/apk/release/app-release.apk`. This is the
  quickest way to verify a change compiles; it does **not** re-run config
  plugins (see the `android/` gotchas above) so it's only valid once
  `android/` already reflects your source changes.
- **`./build.sh` / `./build.sh --clean`**: the full interactive pipeline —
  drafts a changelog via `scripts/prepare-changelog.js`, optionally regenerates
  `android/` from scratch (`--clean`, destructive to any untracked native
  edits — see gotchas above), builds, and optionally publishes.
- **`npm run publish`** (`publish-github.js`): builds and creates/updates a
  GitHub Release tagged `vX.Y.Z` with the APK attached; this is what the
  in-app `OTAUpdateChecker` polls for.
- **Versioning**: bump `version` in both `package.json` and `app.json`, and
  always increment `android.versionCode` in `app.json`. Add a
  `changelogs/vX.Y.Z.md` (the prepare-changelog script drafts one from the
  diff) and fold a summary into `CHANGELOG.md`.

## Working in this dev environment

There is normally **no physical device or emulator available** on this
machine — a KVM-backed emulator was tried once and was too slow for the
system to run usefully, so don't default to spinning one up. Verification
options, in order of preference:
1. `npx tsc --noEmit -p .` for JS/TS changes.
2. `cd android && ./gradlew assembleRelease` for native/Kotlin changes — a
   clean `BUILD SUCCESSFUL` is meaningful (resource collisions, missing
   symbols, and manifest errors all surface here), but it cannot catch
   runtime-only bugs (native module collisions, RemoteViews rendering, launcher
   quirks). Say so explicitly rather than claiming a build proves correctness.
3. Hand the resulting APK to the user to sideload and test on their own phone
   — this is the actual test environment for anything native/visual. Copy it
   to the repo root with a descriptive suffix (`CatalystEssentials_<timestamp>_<what>.apk`,
   matching `build.sh`'s naming) so it's easy to find; it's already
   `.gitignore`d, don't try to commit it.
